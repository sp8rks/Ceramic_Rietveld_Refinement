# 7h. The GSAS and GSAS-II readers and writers: what their files do not carry

Load it when you read a GSAS `.EXP` or a GSAS-II `.gpx` project file, a GSAS `.prm` or `.iparm` or a GSAS-II `.instprm` instrument-parameter file (a constant-wavelength or a time-of-flight one), or when you write one of those back or export a phase CIF for GSAS-II, and a `Diagnostic` came with it.

*A reference file of the `rietx` skill. The body it belongs to is [`SKILL.md`](../SKILL.md); section numbers are the ones the body cites.*

These are the codes of `rietx.io.projects.gsas` and `rietx.io.projects.gsas2`,
together with the instrument-file and phase-CIF pairs `rx.read_gsas_prm` /
`rx.write_gsas_prm`, `rx.read_gsas2_instprm` / `rx.write_gsas2_instprm` and
`rx.write_gsas2_phase_cif`. They are §7g's channel and not the engine's: a
reader or a writer emits them into a list you pass in
(`rx.read_gsas_exp(..., diagnostics=[])`, `rx.read_gsas2_gpx(...,
diagnostics=[])`, `rx.read_gsas_prm(..., diagnostics=[])`), and none of them
ever reaches `result.diagnostics`. §7g,
[`references/diagnostics-projects.md`](diagnostics-projects.md), states that
rule in full and holds the TOPAS and FullProf rows.

The two programs share a file because their row sets are parallel and a
migration reads them against each other. Five of the `.EXP` suffixes are also
`.gpx` suffixes, and two of the `.prm` ones are also `.instprm` ones, so the
row you want sits beside the row you are comparing it with. The **writer** rows
are here too. A `.EXP`, a `.prm`, an `.instprm` and a GSAS-II phase CIF are all
written back, this build writing no `.gpx`, and what a writer could not carry is
as much a difference from the other program's answer as what a reader could not
read.

Each row states, as the others do, what you must *not* assume once it fires.
Two conventions run across the family. A reader **repairs and reports** where
the repair is a stated, recoverable loss and **refuses** where carrying on
would mean choosing between two readings of the file — so an `_NORMALISED` or
`_DROPPED` code is a repair you can undo, and a `_REFUSED` one is a build that
did not happen. And every construct a format can write is classified in
`rietx.io.projects.coverage`, one row per feature, so support for a construct
arrives by moving its row rather than by growing a reader.

| code | what you must not assume, and what to do |
|---|---|
| `GSAS_EXP_HISTOGRAM_NOT_READ` | (warning — from the GSAS `.EXP` reader: pass `read_gsas_exp(..., diagnostics=[])` to collect it, or `read_project_model(..., diagnostics=[])`; it is not on `result.diagnostics`) Assume every histogram in the file reached the model. One did not: it is single-crystal data, or it is time-of-flight or energy-dispersive rather than constant-wavelength, whose profile functions number their coefficients differently. The histogram is still on `model.histograms` with its wavelengths and ranges; what is missing is its **named** profile coefficients, because naming them under a constant-wavelength function's order would mis-assign every width. `model.unsupported` carries the same lines whether or not a `diagnostics=` list was passed |
| `GSAS_EXP_BACKGROUND_NOT_CARRIED` | (info — from the GSAS `.EXP` reader, same channel) Assume the background crossed over. It did not, and it mostly cannot: GSAS's seven background functions include a reciprocal-Q expansion for air scatter and a linear interpolation between fixed points, neither of which is a rietx background. The function number and its coefficients are on `model.histograms[…].background`, so you can see what shape the run fitted; choose your own background and refine it rather than converting the numbers. This is why an Rwp you compute is not comparable with the file's until you have matched the background too |
| `GSAS_EXP_PHASE_MAGNETIC` | (warning — from the GSAS `.EXP` reader, same channel) Assume the phase is nuclear. GSAS phase types 2 and 3 are magnetic, and this reader does not read a `.EXP` magnetic block yet (the operators with their time-reversal signs and the site moments), so `to_structure` **refuses** it rather than handing back the nuclear half — which would look complete. The cell and sites are readable on `model.phases`. A magCIF of the same structure is the route that reads: `Structure.from_cif` (§7j, `references/magnetic.md`) |
| `GSAS_EXP_SPECIES_NORMALISED` | (info — from the GSAS `.EXP` reader, reported at **build**: pass `diagnostics=` to `to_structure`) Assume the built structure's species are the file's literal tokens. GSAS writes them in upper case (`CA`, `NA`) and the reader title-cases them onto IUCr spelling (`Ca`, `Na`) for the `Structure`, which carries only the one form. An isotope type, `aasv_nnn`, takes its number in front as the mass number (`NI+2_58` → `58Ni2+`; issue #555). `read_gsas_exp` keeps the file's own spelling on `model.phases[…].atoms[…].species`, so the model stays checkable against the file. The `.EXP` sibling of `CIF_SPECIES_NORMALISED` and `FULLPROF_SPECIES_NORMALISED` |
| `GSAS_EXP_COORDINATES_SYMMETRY_FIXED` | (info — from the GSAS `.EXP` reader, reported at build) Assume a site carrying GSAS's `X` refine flag has free coordinates. GSAS's flag means "refine **as permitted by symmetry**", and these sites sit on fully fixed special positions, so nothing of them was free in GSAS either. Carrying the flag onto `x`/`y`/`z` directly would make the whole import raise, because rietx refines coordinates as site-symmetry DOFs and a zero-DOF site refuses a vary request. Nothing is lost here and the parameter count is right; the row exists so that "this site is held" reads as the file's statement rather than as the reader's omission. `where` names the sites |
| `GSAS_EXP_SCALE_NOT_COMPARABLE` | (info — from the GSAS `.EXP` reader, reported at build) Assume the phase scale came from the file. It did not: it is seeded at 1e-3 and left to refine. GSAS's histogram scale folds its own profile normalisation and the phase fraction into one number, so it is not a rietx scale and converting it would be inventing a correspondence. The file's own numbers are on `model.histograms[…].scale` and `model.hap[…].phase_fraction`. Refine the scale rather than trusting a converted value — and for the same reason, phase fractions from the two codes are comparable only after both have refined |
| `GSAS_EXP_VALUE_NARROWED` | (info — from the GSAS `.EXP` **writer**: pass `write_gsas_exp(..., diagnostics=[])` to collect it) Assume a written value is the value you had. A `.EXP` is read by column, so a number is worth exactly the ten characters its field holds; one whose shortest exact decimal is longer is written to the precision the field carries. The row fires once for the file, naming how many values and the worst of them, and `where` lists every one. A displacement is always among them, since GSAS stores `Uiso` and rietx stores `Biso` and the 8π² between them makes every `Biso` a long `Uiso`: about seven significant figures survive, 1e-7 of the value against an esd of ~1e-2, and two figures better than the six decimals GSAS itself writes. Nothing to act on unless you are comparing bit patterns |
| `GSAS_EXP_REFINE_FLAG_MERGED` | (warning — from the GSAS `.EXP` writer, same channel) Assume the file's refine flags are your `Structure`'s. GSAS states **one** flag for a whole cell and one `X` letter for a site's three coordinates, both meaning "refine as symmetry permits", where rietx carries a `vary` per parameter. Where a group's members disagree the flag is written **free**, so the file frees a parameter you held, and the row names the group. Reading the file back gives every member of that group the one flag, so this is the one place a round trip does not return what it was given. Hold the whole group, or free it, if the distinction matters |
| `GSAS_EXP_SPECIES_WRITTEN_NEUTRAL` | (warning — from the GSAS `.EXP` writer, same channel) Assume the exported file carries the ion your species label names. rietx's X-ray table has no such ion (`Fe+`, `S2-`), so rietx computed the neutral atom for it (`SPECIES_FALLBACK_NEUTRAL` at fit time), and the atom type is that neutral element (`FE`). No writer writes an atom rietx did not compute, and none refuses a species for its charge (WP-1527). `value` is the fractional error on \|f\| at s = 0 and `where` lists every site. To refine the ion in GSAS, respell the type there. A digitless ion the table carries is not named: `Cu+` is written `CU+1` |
| `GSAS2_GPX_ITEM_NOT_READ` | (warning — from the GSAS-II `.gpx` reader: pass `read_gsas2_gpx(..., diagnostics=[])` to collect it, or `read_project_model(..., diagnostics=[])`; it is not on `result.diagnostics`) Assume everything in the project reached the model. A `.gpx` is a whole GSAS-II session and this reader takes the powder half of it: an image, a single-crystal histogram, a sequential-fit result and a restraint set are each named here and carried nowhere. A **time-of-flight** histogram is the case to watch — it is on `model.histograms` with its numbers, but its coefficients are a different profile function from the one this build fits, so `Gsas2Histogram.constant_wavelength` is what decides whether the terms mean what their names suggest. `model.unsupported` carries the same lines whether or not you passed a list |
| `GSAS2_GPX_BACKGROUND_NOT_CARRIED` | (info — from the GSAS-II `.gpx` reader, same channel) Assume the background crossed over. GSAS-II's own function name and its coefficients are on `model.histograms[…].background`, including the Debye terms and fitted background peaks it counts separately, and none of it is converted: choose your own background and refine it. This is why an Rwp you compute is not comparable with the file's until you have matched the background too — the `.EXP` sibling of this row says the same thing about the older format |
| `GSAS2_GPX_PHASE_MAGNETIC` | (warning or info — from the GSAS-II `.gpx` reader, same channel) Assume the project is purely nuclear. It fires in **two** shapes. A phase GSAS-II types `magnetic` (warning) is refused outright by `to_structure`, because this reader does not read a `.gpx` magnetic block yet and the nuclear half would look complete — the `.EXP` reader's stance; a magCIF of the same structure reads through `Structure.from_cif`. The project's other phases build, but where they share a histogram with it the file's figures include its magnetic scattering, so a fit of them alone is not the same measurement. A phase typed `nuclear` that carries GSAS-II's `magPhases` entry (`Gsas2Phase.magnetic_partner`) builds, and the row says what the file shows: whether the entry is one of the project's histogram names, and how many magnetic phases the project holds. With none it is **info**: nothing magnetic is modelled, and the file's Rwp is a nuclear figure. (Measured, #606: on the five public projects checked that carry the entry it is a histogram name and there is no magnetic phase.) The entry is kept verbatim and not interpreted, since GSAS-II does not document it |
| `GSAS2_GPX_CONSTRAINT_NOT_CARRIED` | (warning — from the GSAS-II `.gpx` reader, same channel) Assume the constraints came with the model. They did not: `to_structure` applies none of them, because a tie between parameters the build has not made yet is not a tie. They are on `model.constraints`, each printing as the relation it states, and `Gsas2Constraint.is_equivalence` marks the ones `Refinement.tie_equal` restores in one call each — the count in the message is how many. A hold (`kind == 'h'`) is a `set_vary(path, False)`; a constraint equation and a new variable have no one-call equivalent, so read them before assuming your free set matches the file's |
| `GSAS2_GPX_SPECIES_NORMALISED` | (info — from the GSAS-II `.gpx` reader, reported at **build**: pass `diagnostics=` to `to_structure`) Assume the built structure's species are the file's literal tokens. GSAS-II writes an ionic charge sign first (`Mn+3`, `O-2`) and the reader rewrites it to IUCr spelling (`Mn3+`, `O2-`) for the `Structure`, which carries only the one form. It also names an isotope the phase's `General['Isotope']` chose, which becomes the mass number in front (`H` with `2` → `2H`; issue #554). `read_gsas2_gpx` keeps the file's own spelling on `model.phases[…].atoms[…].species`, so the model stays checkable against the file. The `.gpx` sibling of `CIF_SPECIES_NORMALISED` and `FULLPROF_SPECIES_NORMALISED` |
| `GSAS2_GPX_COORDINATES_SYMMETRY_FIXED` | (info — from the GSAS-II `.gpx` reader, reported at build) Assume a site carrying GSAS-II's `X` refine flag has free coordinates. That flag means "refine **as permitted by symmetry**", and these sites sit on fully fixed special positions, so nothing of them was free in GSAS-II either. Carrying the flag onto `x`/`y`/`z` directly would make the whole import raise, because rietx refines coordinates as site-symmetry DOFs and a zero-DOF site refuses a vary request. Nothing is lost and the parameter count is right; the row exists so that "this site is held" reads as the file's statement rather than as the reader's omission |
| `GSAS2_GPX_SCALE_NOT_COMPARABLE` | (info — from the GSAS-II `.gpx` reader, reported at build) Assume the phase scale came from the file. It did not: it is seeded at 1e-3 and left to refine. GSAS-II keeps a histogram scale *and* a per-phase scale, each folding its own normalisation into one number, so neither is a rietx scale and converting one would be inventing a correspondence. The file's numbers are on `model.histograms[…].sample['Scale']` and `model.hap[…].scale`. Refine the scale rather than trusting a converted value — and for the same reason, phase fractions from the two codes are comparable only after both have refined |
| `GSAS2_GPX_SETTING_FROM_OPERATORS` | (info — from the GSAS-II `.gpx` reader: pass `read_gsas2_gpx(..., diagnostics=[])`) Assume the phase was built under the symbol the file wrote. It was built under the setting the file's **operators** describe, which need not be the same: GSAS-II stores the operations themselves (`SGData['SGOps']`), so a bare two-setting symbol like `F d d d` is settled by the file rather than by gemmi's reading of its name — and in all four tutorial-corpus phases that write one, the operators are origin choice 2 where the bare symbol resolves to choice 1. Nothing is lost and nothing is owed; the row exists because the built `Structure` then carries a symbol (`'F d d d:2'`) that is not the string in the file, which `Gsas2Phase.space_group` still holds beside `.resolved_space_group`. It is also why the `.gpx` route does **not** raise `SPACE_GROUP_SETTING_ASSUMED` where the `.EXP` and `.inp` routes do: those formats state a symbol and no operators, so nothing in them can settle it and the reader says so at read rather than leaving it to a fit |
| `GSAS_FIELD_OVERFLOW` | (warning — from `rx.read_gsas_exp` and `rx.read_gsas_prm`, same channel) Assume a `None` on the model means the file left the field out. Here it wrote one: the field is all asterisks, which is Fortran's output when a value is too wide for its edit descriptor, so GSAS had a number and ran out of columns. It fires only for an **optional** field (an esd, the history `RPOWD` Rwp, `KRATIO`), which reads as absent; the row names the record key in `where` and the card columns in the message. An overflow in a **required** field (a cell edge, a coordinate, a `.prm`'s `LAM1`) refuses the read and says overflow, and so does one in a profile or background coefficient, whose position is its name. Take the value from GSAS's own listing if you need it |
| `GSAS_PRM_FIELD_DROPPED` | (info — from `rx.read_gsas_prm`, same channel) Assume the returned `Instrument` carries everything the `.prm` states. It carries what `ProfileTCHZ` and `Geometry` have room for, and one of these fires per record that held something else **at its identity value**: `ICONS` (a zero `LAM2` or `ZERO`, the polarization type `IPOLA`, the refine flags and `IDAMP`, and `KRATIO` where the file states no second line to weight), `PRCF` (`GP` and every coefficient past position 8, all 0), and `IRAD`/`ITYP`, ignored by design because the wavelength is read from `ICONS` rather than looked up and an angular range belongs to the pattern. A **non-zero** value in any of those raises instead of reporting: the rule is refuse at drift, report at the model's identity, so an `info` here means the file agreed with the model rather than that something was lost. `where` names the record. **A file stating a doublet comes back with two emission lines**, the second weighted by `KRATIO`, and the `ICONS` row says so — so do not add a Kα2 line yourself after reading one (Measured: WP-1118). **An `HTYPE PNCR` file's `POLA` is the one non-zero value dropped rather than refused**: a neutron source pins its polarisation term at 1, so the value cannot change the instrument, and the `ICONS` row names it as read and not applied (Measured: WP-1312, HB-2A's `POLA 0.990`) |
| `GSAS_PRM_GEOMETRY_ASSUMED` | (warning — from `rx.read_gsas_prm`, same channel) **Do not assume the geometry was read: a `.prm` does not state one.** `HTYPE PXCR` spans Bragg-Brentano and Debye-Scherrer and the format gives nothing to tell them apart, so the reader returns `Instrument.debye_scherrer` — a capillary, `packing_fraction=0.6` — because that is what the corpus behind the reader is, and fires this every time rather than inferring. It matters more than a dropped zero: `Geometry.kind` selects the position correction and its suggested action, and the two geometries' absorption corrections have different *off* states (`mu_r = 0` against `mu_t = ∞`), so a flat-plate calibration read this way arrives with the wrong half of that machinery armed. If the calibration is from a flat-plate diffractometer, set the geometry yourself before fitting — and **carry `geometry.axial_sl` and `geometry.axial_hl` over to the replacement**, because `PRCF` positions 7-8 (`S/L`, `H/L`) were read from the file and land on the geometry, so a `Geometry` built from scratch has no axial divergence at all. On an `HTYPE PNCR` file the instrument is `Instrument.constant_wavelength_neutron` instead, also Debye-Scherrer, and the message names that preset rather than the capillary corpus (Measured: WP-1312) |
| `GSAS_PRM_PROFILE_SET_DEFAULTED` | (warning — from `rx.read_gsas_prm`, same channel) Assume a `.prm` states one profile function. A bank may offer several as profile sets `PRCF1`, `PRCF2`…, and with no `profile_set=` the reader read set 1, as GSAS-II's importer does. The message lists each set's type. Only type 3 is read, so name another type-3 set with `profile_set=N` if set 1 is not the calibration you meant. A type-1 set 1 beside a type-3 set is refused, and the refusal names the set to pass (Measured: WP-1543, GSAS-II's `BT1_Cu311.inst`) |
| `GSAS_PRM_FIELD_NOT_WRITTEN` | (warning — from `rx.write_gsas_prm`: pass `diagnostics=[]`) Assume an exported `.prm` is your whole instrument. It is what GSAS's own `ICONS` and `PRCF` records can state, and the geometry is never among that: a `.prm` states none at all, so the kind, the sample displacement and transparency and the specimen absorption stay behind and reading the file back gives `debye_scherrer` — the writer's side of `GSAS_PRM_GEOMETRY_ASSUMED` above, and the reason `S/L` and `H/L` are worth noticing, being the two geometry numbers that do cross. The row also names a true-Voigt profile (GSAS's type 3 is a pseudo-Voigt with no Voigt option, so the widths cross and the shape model becomes the target's), any `extra_components`, and the refine flags, which an instrument file deliberately does not carry |
| `GSAS_PRM_VALUE_NARROWED` | (info — from `rx.write_gsas_prm`: pass `diagnostics=[]`) Assume an exported `.prm` holds your numbers to the last digit. A `.prm` is read by column and a column is the budget, so a value needing more characters than its field holds was written to what fits, the largest change named. On a converged calibration this is the ordinary case rather than a warning sign: the centidegree conversion adds the product's own float noise, so a `u` of 0.0043710000000001 becomes a `GU` of 43.710000000000996 and then the characters the field allows. The `.prm` twin of `GSAS_EXP_VALUE_NARROWED` |
| `GSAS2_INSTPRM_CONVENTION_ASSUMED` | (info — from `rx.read_gsas2_instprm`: pass `diagnostics=[]`) Assume the two axial-divergence terms are the file's own numbers. GSAS-II models one combined `(S+H)/L` where this package holds `axial_sl` and `axial_hl`, so the single number was split evenly — the symmetric Finger-Cox-Jephcoat reading, and the only one a single number admits. `rx.read_recipe` makes the same split for the same field. If you know the slit and detector heights differ, set the pair yourself |
| `GSAS2_INSTPRM_GEOMETRY_ASSUMED` | (warning — same reader) **Do not assume the geometry was read: this file stated no `Diff-type`.** The fallback is GSAS-II's own — a stated Kα doublet is Bragg-Brentano and anything else Debye-Scherrer — and the two differ in more than a name: a different position correction, and absorption corrections whose off states are opposite (µR = 0 against µt = ∞). Set `geometry.kind` yourself if you know the diffractometer, and carry `axial_sl`/`axial_hl` over first, since `SH/L` *was* read from the file and a fresh `Geometry` starts both at 0 |
| `GSAS2_INSTPRM_VALUE_DEFAULTED` | (warning — same reader) Assume every coefficient came from the file. The named items are absent from it and came back at this package's defaults. GSAS-II writes every item of a bank and its own header says not to delete any, so a missing one means the file was hand-edited — check the values it does state before trusting the instrument |
| `GSAS2_INSTPRM_FIELD_NOT_READ` | (info — same reader) Assume the whole file crossed. The named items have no place in an `Instrument`: `Bank` names a detector rather than describing one, `InstrName` is a name, and on a `PNC` (neutron) bank `Polariz.` is inert in **both** packages — GSAS-II applies the polarization factor only to an `XC` or `XB` type, and `NeutronSource` pins K = 1 |
| `GSAS2_INSTPRM_VALUE_MERGED` | (warning — from `rx.write_gsas2_instprm`: pass `diagnostics=[]`) Assume the file round-trips your axial pair. `axial_sl` and `axial_hl` are written as their **sum**, GSAS-II modelling one number, so reading the file back gives half the sum twice. The row fires only where the two differ, which is the one case the merge loses something |
| `GSAS2_INSTPRM_VALUE_FLOORED` | (warning — same writer) Assume GSAS-II will model the `SH/L` this file states. It floors the value at 0.002 when it evaluates a profile, so a smaller sum is written faithfully and modelled as the floor by the program the file is *for*. No round trip through this package can show it: the floor is the other reader's, not the file's |
| `GSAS2_INSTPRM_FIELD_NOT_WRITTEN` | (warning — same writer) Assume an exported `.instprm` is your whole instrument. It is what GSAS-II's own instrument items can state: never the background, the specimen absorption, the sample displacement or the transparency, which that program keeps in its *sample* parameters, and never the refine flags, a calibration having refined nothing by the time it ships. A true-Voigt profile is named here too — GSAS-II's constant-wavelength function is a TCH pseudo-Voigt with no Voigt option, so the widths cross and the shape model becomes the target's |
| `GSAS2_CIF_SETTING_IN_OPERATORS` | (info — from `rx.write_gsas2_phase_cif`: pass `diagnostics=[]`) Assume the exported CIF's H-M symbol states this phase's setting. It cannot: GSAS-II resolves a bare two-origin symbol such as `F d -3 m` to origin choice **2** and answers a colon-suffixed one by setting the phase to `P 1`, while gemmi resolves the same bare string to choice **1**. So the file states the setting three times — the bare symbol in `_symmetry_space_group_name_H-M`, the resolved one in `_space_group_name_H-M_alt`, and the operations in `_space_group_symop_operation_xyz`, which is the channel GSAS-II checks its own reading against. Nothing is lost; read the operations, never the symbol, if a third program opens the file |
| `GSAS2_CIF_DEUTERIUM_AS_D` | (info — same writer) Assume a deuterium site crosses with the scattering length you refined. It is written `D` (`2H` is respelled), the one isotope label GSAS-II's import takes, and GSAS-II scatters D at its own b = 6.681 fm against rietx's 6.671 fm (Sears), so that refinement starts 0.15 % away on those sites |
| `GSAS2_CIF_SPECIES_WRITTEN_NEUTRAL` | (warning — same writer) The phase-CIF twin of `GSAS_EXP_SPECIES_WRITTEN_NEUTRAL`: `_atom_site_type_symbol` is the neutral element (`Fe` for `Fe+`). `Cu+` is written `Cu1+`, which GSAS-II stores as `Cu+1`; its importer reads a bare `Cu+` as carbon |
| `GSAS2_CIF_RHOMBOHEDRAL_RESTATED` | (warning — from `write_gsas2_phase_cif`: pass `diagnostics=[]`) Assume the phase was already in hexagonal axes. It was on rhombohedral axes, which GSAS-II's CIF import refuses ("a space group setting not compatible with GSAS-II"), so the CIF has the hexagonal cell of the same lattice, held, and the scale divided by 9 (a CIF carries no scale). Same crystal; free what you mean to refine |
| `GSAS2_CIF_FIELD_NOT_WRITTEN` | (warning — same writer) Assume a GSAS-II project built from this CIF starts where your refinement did. A phase CIF states no refine flags, no phase scale and no sample broadening, so that program starts from its own defaults for all three, and any Stephens strain, preferred orientation, extinction or restraints the phase carries are named here because a CIF has no tags for them |

## The time-of-flight instrument-parameter readers

`rietx.io.instrument_tof`'s two readers open a bank's *calibration*, never a
model — no phase, no structure, so `rietx.io.projects.coverage` has nothing to
classify — which is why their codes sit beside the other GSAS and GSAS-II instrument
rows and not with the project families of §7g: they answer the same question ("is what I just imported the
file I meant to import"), about a bank instead of a phase. This build reads
a bank and refines none.

| code | what you must not assume, and what to do |
|---|---|
| `GSAS_IPARM_PROFILE_DECLINED` | (info — from `rx.read_gsas_tof_iparm`, same channel) **Do not assume the returned bank carries the file's peak shape.** Emitted for a `PRCF` set that was *not* read: a non-default set (set 1 is the default whatever its type, and is the only one read), or a bank with no `PRCF` set at all, which then carries its calibration and an all-zero `ProfileTOF`, which says no profile was read. A default set the package cannot read (wrong `NCOF`, profile type 2/4/5, a non-zero anisotropic term) is **refused** at read rather than declined. Declare `instrument.source.profile_tof` by hand, or read the bank's `.instprm`, whose keys are named and whose profile *is* read |
| `GSAS_IPARM_PROFILE_READ` | (info — from `rx.read_gsas_tof_iparm`, same channel) **Check the coefficients before you refine on them: the record order is an assumption.** The default `PRCF` set (type 1 with 12 coefficients, or type 3 with 21) was read onto `instrument.source.profile_tof` in the order the GSAS manual lists the names; the manual never states that this is the record order. `CTOF` is quoted and not used. Everything read arrives `vary=False`, like the calibration beside it |
| `GSAS_IPARM_FIELD_DROPPED` | (info — from `rx.read_gsas_tof_iparm`, same channel) Assume the returned banks carry everything the file states. They carry `ICONS` (DIFC/DIFA/ZERO) and `BNKPAR` (DIST as L₂, TTHETA as the bank's 2θ); this names the records and fields that did not come across, among them `FPATH1` (not a record the GSAS manual lists, so L₁ stays unset) and `ITYP`'s `CHKSUM` (its algorithm is unpublished). `ITYP`/`ICOFF`/`IECOF` are the incident-spectrum function, its coefficients and their esds, and those **are** read onto `instrument.source.incident_spectrum`. What is dropped beside them is `IECOR`, the coefficients' correlation matrix, which has no slot. `BNKNAM`, `MFIL` and `HEAD` are labels. Fires once per file, `where` listing the records |
| `GSAS_IPARM_LEGACY_LAYOUT` | (info — from `rietx.io.legacy.read_lansce_iparm`, same channel) **Do not assume the file met the GSAS manual's layout; it met the legacy LANSCE one.** Each report names one of three deviations by its last `where` entry. `PRCF1`: the default set was a type-1 block of 8 coefficients, read as the first eight of the documented twelve (slots 9-12 zero) and then through the strict reader, so the `GSAS_IPARM_PROFILE_READ` beside it describes that restated block; slots 1, 5, 8 are `alp-0`, `sig-0`, `s1ec` by the manual's order, which GSAS-II leaves unnamed. `ICOFF3`: a non-zero ITYP 1/2 fifth pair, carried as written. `BNKPAR`: that one record ran a value across a field boundary and was re-read by tokens; the message quotes the raw text and the value taken, so check the angle.
