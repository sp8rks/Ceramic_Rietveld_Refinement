# 7i. The readers: what was changed, assumed or noticed about your own file

Load it when you passed `diagnostics=[]` to `read_pattern`, `Structure.from_cif`, `RefinementTree.load` or `load_instrument_profile` and something came back, or when one of these codes reached `result.diagnostics`.

*A reference file of the `rietx` skill. The body it belongs to is [`SKILL.md`](../SKILL.md); section numbers are the ones the body cites.*

These fire on **your own** data and structure files, at the read, and each one
is conditional on a quirk that file happens to have. That separates them from
§7, and the channel they arrive on does not: most of them also reach
`result.diagnostics`, and several of §7's own rows are equally the reader's.
They are here because of how often you will meet one. A vendor attenuator, a
scan stored backwards, a dead detector cell: none of these is a thing a fit
does, and a table an agent loads to look up what its fit just said should not
be carrying rows about file quirks it does not have.

They share the readers' rule. A reader may repair a stranger's file only where
it can say that it did, so every repair below is on this channel and none of
them is silent. A reader that cannot establish something **withholds** it, and
two of these rows are about a number you are therefore not being given.

Two families sit elsewhere. Another program's project or recipe file is §7g,
[`diagnostics-projects.md`](diagnostics-projects.md). What a file you *wrote*
could not carry is §7h, [`diagnostics-gsas.md`](diagnostics-gsas.md).

| Code | What it means you must not do |
|---|---|
| `CIF_SPECIES_NORMALISED` | (info — from the reader: pass `Structure.from_cif(..., diagnostics=[])` to collect it; it is not on `result.diagnostics`) Assume the model's species are the file's literal type symbols. The reader rewrote a wild form — a site label in the type-symbol column (`O1`) or a sign-first charge (`O-2`) — onto the canonical grammar, keeping the ion when one was written; each message names its substitution and `where` lists the atoms it touched |
| `CIF_CELL_ANGLE_CORRECTED` | (warning — from the reader, same channel as `CIF_SPECIES_NORMALISED`) Assume the cell is the file's. A symmetry-fixed angle disagreed with its space group by a *reportable* amount (up to 0.1°) and was read at the exact value, because `ParameterTable` refuses such a cell and has no channel to say why. The deviation is information: if it is real, the symmetry is lower than the symbol claims. A disagreement beyond 0.1° is **not** corrected — it still raises, because the symbol and the angle contradict each other and choosing between them is yours |
| `CIF_SITE_MULTIPLICITY_DISAGREES` | (warning — from the reader, same channel) Assume the site has the multiplicity its coordinates give. The file states another one (`_atom_site_symmetry_multiplicity` or the number in `_atom_site_Wyckoff_symbol`) and moving the site by up to 1e-3 does not reach it, so nothing was moved. (Where it *does* reach it, the reader moves the site onto that position and `SITE_SNAPPED_TO_SPECIAL_POSITION` says so.) The atoms in the cell, hence ZMV and every weight fraction, follow the coordinates. Check the space-group setting and the site against the source |
| `CIF_SITE_TWINS_MERGED` | (warning — from the reader, same channel as `CIF_SPECIES_NORMALISED`) Assume the site's coordinates are the file's — they were moved onto a special position. Its own images sat closer than 0.02 Å apart (a special position printed off by its rounding, e.g. (0.828, 0.657, ¼) for (x, 2x, ¼)), so every image had a twin and the site would scatter twice. `value` is the twin distance in Å |
| `CIF_SITE_LISTED_TWICE` | (warning — same reader, same channel) Assume every listed site is in the phase — one was dropped. It lay within 0.02 Å of an image of an earlier site of the same species and occupancy (and, for a magnetic site, carried that image's moment), so the file listed one orbit twice and both would have counted. A copy that differs in occupancy, displacement, disorder group or moment is refused instead |
| `DECLARED_RANGE_RESTORED` | (warning, or info when only a unit came back — from the history and instrument-profile readers: pass `diagnostics=[]` to `RefinementTree.load` or `load_instrument_profile`, or read `Project.history_diagnostics` after `Project.open`) Assume a reopened model refines exactly as the run that wrote it did. A release before that parameter's class inherited its declared range left a caller's own `Parameter(value=...)` at (-inf, inf), no unit and `identity` (issue #204, where an Fe Biso reached −165 Å² at unchanged Rwp); the reader put the declared range and transform back in every node that stored it, and no value moved. A range of your own goes on the `Parameter` explicitly, and wins |
| `DECLARED_RANGE_NOT_RESTORED` | (warning — the same channel as `DECLARED_RANGE_RESTORED`) Trust that parameter's value, or assume it is bounded: it is not. The same release left it unbounded, but a stored value lies outside the range its field declares, so it was left as stored everywhere rather than handed a range that refuses the record. `value` is the first such value and the message names where it is stored. A real measurement outside a default box, such as a coarse neutron line's Caglioti `u`, gets a range that holds it before the next fit; anything else is the unbounded walk #204 describes and not a number to quote |
| `PATTERN_SCAN_REVERSED` | (info — from the pattern reader: pass `read_pattern(..., diagnostics=[])` to collect it) Assume the point order in the file is the point order you are fitting. The scan was stored high 2θ → low and was reversed, which is lossless — the same measurement written backwards — but it means an index into the file is not an index into the pattern |
| `PATTERN_DUPLICATE_POINTS` | (info — from the reader) Quote the file's point count as the fitted channel count. One or more 2θ values appeared twice with the *same* intensity and the repeats were dropped. A repeat with a *different* intensity is not reported here: it raises, because averaging invents a datum and dropping picks one |
| `PATTERN_ROWS_DROPPED` | (warning — from the reader) Quote the file's line count as its point count. Rows whose column count differs from the file's most common one were not read as data, and `where` lists their line numbers. A numeric header row (a detector table, an integration-limits row) is the usual cause: PDFgetX2's header put a phantom point at (0, 1) on every file one user had. If a dropped row is a measured point, the file mixes column counts and needs re-exporting. Only the two/three-column reader counts columns |
| `PATTERN_MULTISCAN_DEFAULTED` | (warning — from the reader) Read the result as a fit to the file. The file holds several scans, none was named, and **scan 0** was read — a third of a measurement is a choice, and this one was made by default rather than by you. Pass `scan=` (or `list_scans(path)` first) before quoting anything |
| `PATTERN_X_AXIS_ASSUMED` | (warning — from the reader) Trust the 2θ scale. The file states which axis it scanned and named one this reader does not recognise, so the x column was read as 2θ in degrees. Each format states it somewhere different — `.chi`'s line-2 label, `.ras`'s `*MEAS_SCAN_AXIS_X`, `.uxd`'s `_DRIVE`, `.xrdml`'s `scan/@scanAxis` — and the message names both the field and what it held. The code means **unrecognisable**, never "recognisably not 2θ": an axis that *is* recognisably q, d, ω, χ, φ or a translation is **refused**, because such a scan parses perfectly and refines to a confidently wrong cell. Worth taking seriously — most vendor files are not powder scans (4 of the 5 real `.uxd` files obtained are pole figures or rocking curves), and a block marker is not evidence either: a rocking curve is stored under `_2THETACOUNTS` too |
| `PATTERN_X_AXIS_IMPLAUSIBLE` | (warning — from the reader) Fit the interval it names. The axis starts at or below 0°, where no Bragg reflection lies, and `where` carries the interval to exclude. It is checked for every format after the read. Its other half is a **refusal**: an axis running past 180° raises, because no scattering angle exceeds 180°. That refusal is how a file read in centidegrees surfaces, and its message offers the ÷100 reading when the two/three-column reader took the file and the result lands in range. A point at exactly 0° can be a header row with the data's own column count, which `PATTERN_ROWS_DROPPED` cannot see. Otherwise exclude the interval, or check that the axis is 2θ in degrees |
| `GSAS_BANK_COMMENTED` | (info — from the reader) Nothing, if the file is the measurement. The file had no live `BANK` record, and its first one behind a `#` was read as the bank. Missed, the file fell to the two/three-column reader and came back with 2θ 100× too large, because GSAS writes centidegrees. A file with a live bank beside a commented one reads the live one and says nothing, since commenting a bank out is also how a bank is disabled |
| `PATTERN_INTENSITY_SCALED` | (warning — from the reader) Quote esds, χ² or a σ-normalised residual from this fit as if the weights were measured. The stored intensities are not whole numbers and no counting time in the header makes them whole either, so whether they are counts or a rate **could not be established** — and no σ was supplied. The Poisson fallback √max(y,1) is therefore being applied to a quantity that may already be divided by a counting time, in which case every weight is wrong by √t. The fit still runs and the *parameters* are largely unaffected; it is the uncertainties that are not quotable. Re-export in counts, or supply esds |
| `PATTERN_SIGMA_CONSTANT` | (warning — from the reader) Quote χ², GoF or a σ-normalised residual as if the weights were measured. The σ the reader took is the same number on every point, so every point weighs the same and the fit is unweighted. It is kept, because a uniform σ is legal. The usual cause is a placeholder or flag column where the reader looks for an esd. A two/three-column file gives up any positive third column, and a PDFgetX2 `.sq` has a constant 1.0 there with its real uncertainty in column four. Set `pattern.sigma = None` for Poisson weights, or re-export with the esd where the reader looks. Checked for every format that reads a σ |
| `PATTERN_DEAD_CHANNELS` | (warning) Fit a range that contains them, or read the parameters at their bounds as the cause. A dead or masked detector cell measures a Poisson sample of nothing and its esd fell with its intensity. Weights are 1/σ², so it outvotes a live channel there by the factor the message quotes. On the ILL D1B file this comes from, two cells at σ = 1.0 sit beside background at σ = 55.1 and carry about 3000 live channels each: Rwp 0.087 against 0.0074 with them excluded, every background model dragged through zero at the top of the range, the Caglioti terms at their bounds, every Biso pinned at zero. None of those fourteen bound hits is the problem. `where` carries the interval to exclude, and nothing is excluded for you, since `project.fitted_mask` is the caller's. It needs the file's own σ column: under the Poisson fallback √max(y,1) a dead cell and a channel that honestly counted zero are the same pair of numbers, so a pattern with no esds emits nothing here and the silence is not an all-clear. Also on `PatternDiagnostics.dead_channels` before any refinement, from `diagnose(data)`, and on the `diagnostics=` list `read_pattern` takes |
| `RAS_ATTENUATOR_PRESENT` | (warning — from the reader) Compare intensities across the 2θ range this names. A Rigaku `.ras` or `.rasx` carried an attenuator factor that is not 1, and it was **not** applied: no specification states whether the intensity column is already corrected for it, so applying it and not applying it are both defensible and guessing corrupts exactly the strong peaks Rietveld weights most. σ is affected too — √counts·attn is not √y. The message names the affected points; check the export against the instrument software before trusting their relative heights. Contrast `XRDML_ATTENUATOR_APPLIED`, where a real file settles what no Rigaku file can |
| `XRDML_ATTENUATOR_APPLIED` | (info — from the reader) Nothing; it is here because the correction is large and invisible in the file's own numbers. A PANalytical beam attenuator dropped a foil in front of the detector for the points named, and the reported intensity is `counts × factor` with σ = √counts·factor — **not** √y. Read it as the opposite of `RAS_ATTENUATOR_PRESENT`: this one is settled, because a real file shows the raw series *dipping* at exactly the attenuated point of a substrate reflection, which is the attenuation and not a profile. A factor of 188 over one point is normal. The case GSAS-II gets wrong, weighting 1/y regardless |
| `BRML_ABSORBER_ENGAGED` | (info — from the reader) Nothing to the intensities; they are already right. A Bruker automatic absorber engaged over the points named, and the stored series is **already corrected** for it, so nothing was multiplied — but those points carry a factor fewer counts than their height suggests, and σ was derived as √(y/a)·a rather than √y. The third answer to one question: `RAS_ATTENUATOR_PRESENT` reports because no Rigaku file settles it, `XRDML_ATTENUATOR_APPLIED` multiplies because a real file shows the raw series dipping, and this one leaves the values alone because a real file shows them continuous |
| `READER_OPTION_IGNORED` | (info — from the reader) Assume a reader option you passed took effect. This format does not take it, so the file was read as if it had not been given — normal when a form carries a value across a change of file, and a mistake when you named a `block` or a `scan` you meant to select. Check `identify_format` claimed the reader you expected |
